## Follow-up migration `e00c25c0041f` (applied after the agent round)

Founder approved the three flagged schema gaps plus the client-binding decision; all four
landed as one migration to keep the chain linear.

1. **`schedules.enqueued_at`** — the calendar bug is fixed. The sweep now marks a schedule
   consumed with `enqueued_at` instead of overloading `is_cancelled`, so published posts
   stay visible in `GET /api/v1/calendar`.
   **Note for reviewers:** the first pass changed only one of the two consume sites, and
   the suite stayed green because the existing tests asserted the *old* semantics. Both
   sites are now converted, the two tests that encoded the bug were rewritten to assert
   the new contract, and a dedicated regression test
   (`test_published_schedule_stays_visible_to_the_calendar`) queries with the same
   predicate the calendar router uses.
2. **`uq_analytics_org_post_captured`** — duplicate rejection is now enforced by the
   database, not just a read-then-write pre-check. `create_snapshot` catches
   `IntegrityError`, matches it by constraint name (so unrelated integrity errors still
   surface as themselves), and raises the same `ConflictError`.
3. **`uq_publish_jobs_live_per_post_account`** — partial unique index over
   `QUEUED/RUNNING/RETRYING`. Verified by direct SQL against the migrated database: a
   second live job is rejected, and a terminal job is still accepted so republishing after
   a settled attempt remains possible.
4. **Client binding (the product decision).** `integration_mounts.default_client_id` binds
   the real customer once, at mount time — an operator action by someone who actually
   knows the customer — instead of the intent path guessing per request. Resolution order
   is now: mount's bound client → brand's client → existing placeholder → new placeholder.
   Placeholders are flagged `clients.is_placeholder = True` and logged at WARNING, so they
   can be listed and merged rather than recognized by name convention.

Hand-edits required in that migration, documented in its docstring: the missing
`import app.core.db_types`; removal of autogenerate's spurious `drop_index` calls for the
two `execution_nodes` composites (the drift documented below — it recurred exactly as
predicted); `server_default=sa.false()` on the new NOT NULL `is_placeholder` column, since
adding one to a table with existing rows fails without it, then dropped so the Python-side
default is the only source; and an explicit name for the new foreign key, because
autogenerate emitted `drop_constraint(None, ...)` in `downgrade()`, which cannot execute.

## What landed this session

### Execution graph (was Priority 1)
`412a32e37eb2` creates `execution_nodes` with the seven single-column indexes the model
declares plus two hand-added composites (`ix_execution_nodes_org_workflow_ref`,
`ix_execution_nodes_org_open`).

**Known wart:** those two composites are not declared on the ORM model, so every future
`alembic revision --autogenerate` proposes dropping them. This already happened once —
migration `11bbfaf5a443` was autogenerated with spurious `drop_index` calls for both and
had to be hand-corrected. Discard that block whenever it reappears. Decided 2026-07-24 to
accept this over adding an `include_object` filter to `alembic/env.py`.

### GTM/WS3.3 intake bridge (was the real gap)
`POST /integrations/social-media-marketing/mount` (204 + `Location`) and
`POST /integrations/social-media-marketing/mount/{mount_id}/intent`. One transaction
creates Campaign → Post(s) → PostVersion v1 → bootstrap Approval → execution graph +
audit row, with full rollback on mid-ingest failure. Migration `11bbfaf5a443` adds
`integration_mounts`.

### Approval workflow
`post.status` is now structurally impossible to write outside `ApprovalStateMachine` — a
`ContextVar` + `@validates` guard on the model raises on any assignment to a persisted or
detached Post. Independently verified non-vacuous: the guard fires, leaves status
unchanged, permits the sanctioned path, and does not leak after the context exits.
Also fixed: `record_decision` could persist an orphan Approval row before an illegal
transition raised; version numbering was racy; `PostVersion` rows were mutable.

### Publishing and scheduling
The most serious findings of the session. Before: publish tasks looked up PublishJob,
Post, and PlatformAccount **by primary key with no `organization_id` filter** — any job id
could publish any tenant's content. Failures were caught and never re-raised. No
idempotence, so a redelivered task double-published. A DRAFT post could be published.
All closed, with an atomic database-level claim for idempotence and execution-graph
status wiring through the existing `WorkflowService`.

### Analytics
Duplicate snapshots now rejected with 409 (application-level; see schema gaps). Weekly KPI
rollup implemented as a dual-dialect ORM aggregation via `app/core/sql_functions.py`.
A real Postgres bug was found and fixed during verification: `date_trunc('week', ...)` on
a `timestamptz` truncates in the **session** time zone, so bucket boundaries varied by
server config. Now pinned with `AT TIME ZONE 'UTC'`.

## Open items

### Contract mismatches with WS3.3, to resolve before going over HTTP
- `mount_id` is a UUID here; WS3.3's `SocialMediaMount.mount_id` is `int` (sqlite
  `lastrowid`). That field must become `str`.
- `brand_id` / `default_brand_id` are UUID FKs here; the plan's JSON shows slugs
  (`"acme-primary"`). WS3.3 must send real UUIDs.
- The plan's `"platforms": ["meta"]` — `"meta"` is not a `PlatformName` member
  (`facebook`/`instagram` are) and will match no adapter at publish time.
